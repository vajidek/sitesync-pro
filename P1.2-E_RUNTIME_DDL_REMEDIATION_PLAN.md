# PHASE 76 REMEDIATION — P1.2-E
## RUNTIME DDL REMEDIATION & DEPRECATION STRATEGY PLAN

---

### 1. OBJECTIVE & SCOPE
With the successful completion of **Phase P1.2-D**, all 642 application tables (including the 356 tables historically created via runtime `CREATE TABLE IF NOT EXISTS` statements) are permanently codified in `src/db/schema.ts` and provisioned in the live PostgreSQL database.

This plan details the safe, phased removal of runtime DDL across all 21 repositories without impacting data integrity, startup time, or business seed routines.

---

### 2. CRITICAL ARCHITECTURAL DISTINCTIONS: DDL VS. SEEDING

| Aspect | Pure Schema DDL | Seed & Business Logic |
|---|---|---|
| **SQL Commands** | `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE`, `CREATE INDEX` | `INSERT INTO`, `SELECT count(*)`, `.insert().values()` |
| **Lifecycle** | Migration time (Drizzle / CI/CD deploy phase) | Application runtime (lazy initialization / first startup seed) |
| **Current Flaw** | Redundant DDL statements executed per request/instance | Embedded inside DDL methods |
| **Target State** | **ELIMINATED** from application code | **PRESERVED & ISOLATED** in pure seed methods |

#### Safety Mandate:
**NEVER convert an `ensure*()` method to a complete no-op if it performs critical seeding or default configuration needed by business queries.**

---

### 3. GUARD VARIABLE & CONCURRENCY ANALYSIS

1. **Instance-Level Guards (`private isTablesEnsured = false`, `private initialized = false`):**
   - **Scope:** Bound to repository class instance.
   - **Flaw:** Multiple callers instantiating new repository instances trigger redundant DDL passes.
   - **Multi-Instance / Serverless Impact:** In horizontally scaled containers or serverless cold starts, every instance independently executes 356 DDL checks against PostgreSQL's system catalogs, creating connection locks and query latency.
2. **Unguarded Repositories (Per-call DDL):**
   - Repositories like `asset_eam.repository.ts`, `finance.repository.ts`, `fleet.repository.ts`, `hr.repository.ts`, `kwa.repository.ts`, `procurement.repository.ts`, `resource.repository.ts`, `dpr.repository.ts`, `document.repository.ts`, `fleet_transport.repository.ts` executed DDL on **every single method invocation**.
   - Eliminating runtime DDL will yield immediate latency reductions (10–50ms saved per API request).

### 5. FRESH DATABASE & MIGRATION-FIRST COMPATIBILITY
1. **Migration Authority:**
   - With `0000_exotic_adam_warlock.sql` and `0001_reconcile_all_tables.sql` applied, any fresh PostgreSQL instance provisioned by running Drizzle migrations will immediately possess all 642 tables.
2. **Deterministic Schema Initialization:**
   - Eliminating runtime DDL guarantees that schema evolution is 100% deterministic and managed exclusively via SQL migrations in `/drizzle`.

---

### 6. PRODUCTION SAFETY & GOVERNANCE
- In this P1.2-E phase, zero code modifications have been made.
- In subsequent authorized remediation (P1.2-F):
  1. DDL blocks will be safely pruned repository by repository.
  2. All seed functions will be kept intact.
  3. `tsc --noEmit` and `npm run build` will verify syntax and typing.
  4. Integration endpoints will be systematically regression-tested.
